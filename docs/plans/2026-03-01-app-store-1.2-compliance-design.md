# App Store Guideline 1.2 Compliance — Design Document

Date: 2026-03-01

## Overview

Full compliance with Apple App Store Review Guideline 1.2 (User Generated Content). The app remains anonymous externally, ephemeral, one-to-one, with no public feed, no profiles, no message history, and no visible user identity. All moderation scaffolding is internal and minimal.

Delivered in 3 PRs: Schema + Backend → Website → iOS.

---

## 1. Schema Changes

All changes in `relay-cafe-api/src/db/schema.ts`. Manual `DELETE FROM messages` before migration.

### 1a. `messages` — Add `sender_user_id`

```sql
ALTER TABLE messages ADD COLUMN sender_user_id UUID NOT NULL REFERENCES users(id);
CREATE INDEX idx_messages_sender ON messages(sender_user_id);
```

Rules:
- NEVER expose `sender_user_id` in API responses
- NEVER log it
- NEVER send it to Sentry
- NEVER return it to client

### 1b. `users` — Add moderation columns

```sql
ALTER TABLE users
  ADD COLUMN suspended BOOLEAN NOT NULL DEFAULT FALSE,
  ADD COLUMN strike_count INT NOT NULL DEFAULT 0,
  ADD COLUMN last_strike_at TIMESTAMPTZ;
```

### 1c. New table: `delivery_log`

```sql
CREATE TABLE delivery_log (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  message_id UUID NOT NULL UNIQUE,
  sender_user_id UUID NOT NULL REFERENCES users(id),
  recipient_user_id UUID NOT NULL REFERENCES users(id),
  delivered_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
CREATE INDEX idx_delivery_recipient ON delivery_log(recipient_user_id);
```

Written atomically inside the receive transaction, before message deletion. Cleaned up by cron after 48h. Audit-only — never replayed.

### 1d. New table: `reports`

```sql
CREATE TABLE reports (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  message_id UUID NOT NULL,
  reporter_user_id UUID NOT NULL REFERENCES users(id),
  sender_user_id UUID NOT NULL REFERENCES users(id),
  action_taken TEXT NOT NULL,
  strike_count_after INT NOT NULL,
  reviewed BOOLEAN NOT NULL DEFAULT FALSE,
  reviewed_at TIMESTAMPTZ,
  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  UNIQUE(message_id, reporter_user_id)
);
CREATE INDEX idx_reports_sender ON reports(sender_user_id);
```

No FK on `message_id` — message is deleted on delivery.

### 1e. New table: `blocked_senders`

```sql
CREATE TABLE blocked_senders (
  blocker_user_id UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  blocked_sender_user_id UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  PRIMARY KEY (blocker_user_id, blocked_sender_user_id)
);
CREATE INDEX idx_blocked_sender ON blocked_senders(blocked_sender_user_id);
```

## 2. Backend API Changes

### 2a. `POST /messages` — Send flow

Entire flow wrapped in a single transaction:

1. **Suspension check** (first):
   ```sql
   SELECT suspended FROM users WHERE id = $userId
   ```
   If suspended → 403 `"Your account has been suspended for violating community guidelines."`

2. **Claim send token** (atomic upsert + update as existing)

3. **Content filter** (before encryption):
   - Lowercase + strip zero-width characters
   - Word-boundary regex matching against curated blocklist
   - Categories: severe slurs, explicit sexual terms, CSAM phrases, violent threats, extreme harassment
   - If matched → 400 `"This message violates community guidelines."`
   - Do NOT store rejected content, do NOT log message text, do NOT send to Sentry

4. **Encrypt + insert** with `sender_user_id`:
   ```ts
   await db.insert(messages).values({
     senderUserId: userId,
     ciphertext, encryptedMessageKey, kmsKeyVersion, iv, expiresAt,
   })
   ```

5. **Commit**

On failure at any step: transaction rolls back, token not consumed.

### 2b. `GET /messages/today` — Receive flow

Modified SQL inside transaction:

```sql
SELECT id, ciphertext, encrypted_message_key, kms_key_version, iv, expires_at, sender_user_id
FROM messages
WHERE expires_at > NOW()
  AND sender_user_id != $currentUserId
  AND sender_user_id NOT IN (
    SELECT blocked_sender_user_id
    FROM blocked_senders
    WHERE blocker_user_id = $currentUserId
  )
ORDER BY RANDOM()
LIMIT 1
FOR UPDATE SKIP LOCKED
```

Transaction order:
1. SELECT ... FOR UPDATE SKIP LOCKED
2. Decrypt
3. INSERT INTO delivery_log (message_id, sender_user_id, recipient_user_id)
4. DELETE FROM messages WHERE id = $msgId
5. Commit

Response: `{id, text, expiresAt}` — `sender_user_id` never returned.

### 2c. `POST /messages/:id/report` — New endpoint

1. Look up `delivery_log` WHERE `message_id = :id AND recipient_user_id = currentUser`
2. If not found → 404
3. Check `reports` for existing row (idempotent — if already reported, return 200 without re-incrementing)
4. Atomic strike increment:
   ```sql
   UPDATE users
   SET strike_count = strike_count + 1, last_strike_at = NOW()
   WHERE id = $senderUserId
   RETURNING strike_count
   ```
5. If `strike_count >= 3` → `UPDATE users SET suspended = TRUE WHERE id = $senderUserId`
6. Insert into `reports` (action_taken: 'removed' or 'suspended', strike_count_after from RETURNING)
7. Return 200 `{ok: true}`

### 2d. `POST /messages/:id/block` — New endpoint

1. Look up `delivery_log` WHERE `message_id = :id AND recipient_user_id = currentUser`
2. If not found → 404
3. INSERT INTO `blocked_senders` ON CONFLICT DO NOTHING (idempotent)
4. Return 200 `{ok: true}`

Blocking does NOT increment strikes. Blocking and reporting are separate.

### 2e. Cleanup cron

Add to existing 10-minute cron in `index.ts`:

```sql
DELETE FROM delivery_log WHERE delivered_at < NOW() - INTERVAL '48 hours'
```

## 3. Website — Community Guidelines

### File: `relay-cafe-site/guidelines.html`

Uses `legal.css`, same structure as `terms.html` and `privacy.html`.

### Content

**Intro:**
> relay.cafe is built for simple, one-to-one human connection. These guidelines exist to keep it safe for everyone.

**Prohibited Content:**
- Hate speech or discrimination
- Harassment or bullying
- Threats or incitement of violence
- Sexual exploitation of minors
- Explicit sexual content
- Illegal activity
- Self-harm encouragement

**Enforcement:**
- We have zero tolerance for content that violates these guidelines.
- Reported content is removed immediately.
- All reports are reviewed within 24 hours.
- Violations result in content removal and account suspension.
- Accounts that repeatedly violate these rules will be permanently suspended.

**How to Report:**
- You can report a message directly within the app using the "Report" button.

**Legal Cooperation:**
- We may cooperate with law enforcement where required by applicable law.

**Contact:**
- safety@relay.cafe (must exist, accept messages, have auto-reply configured before App Store submission)

### Other file changes

- `sitemap.xml`: Add `guidelines.html` entry, priority 0.5
- `index.html` footer: Add "Community Guidelines" link alongside Terms and Privacy

## 4. iOS Changes

### 4a. MessageView — Report + Block buttons

**Layout:** Vertical stack below Close button, centered:

```
Close

Report
Block sender
```

**Styling:**
- Same font as legal links (14pt)
- Opacity 0.45–0.5 (visible for Apple review, not hidden)
- Plain button style
- No heavy animations

**Report flow:**
1. Tap "Report" → alert: "Report this message?" / "The message will be removed and reviewed according to our guidelines." / Cancel + Report
2. On confirm → `APIClient.shared.reportMessage(id:)` → `POST /v1/messages/{id}/report`
3. Dismiss message sheet immediately
4. Show "Message reported." in HomeView status area
5. On 404 (outside 48h window): still show "Message reported." confirmation

**Block flow:**
1. Tap "Block sender" → alert: "Block this sender?" / "You will not receive messages from this sender again." / Cancel + Block
2. On confirm → `APIClient.shared.blockSender(messageId:)` → `POST /v1/messages/{id}/block`
3. Dismiss message sheet
4. Show "Sender blocked."

### 4b. SettingsView — Safety section

Add "Safety" header above existing legal links:

```
Safety
  Community Guidelines    →  SafariView(https://relay.cafe/guidelines)

  "If you encounter inappropriate content,
   use Report in-app or contact us."

  safety@relay.cafe       →  mailto: with clipboard fallback + toast
```

Same styling as existing Terms/Privacy section.

### 4c. APIClient — New methods

```swift
func reportMessage(id: String) async throws    // POST /v1/messages/{id}/report
func blockSender(messageId: String) async throws // POST /v1/messages/{id}/block
```

Both POST with JSON body (even if empty). Handle:
- 200: success
- 401: unauthorized (trigger sign-out)
- 403: suspended
- 404: silently succeed (outside retention window)
- Network errors: do not crash

### 4d. Suspension handling

When `POST /v1/messages` returns 403:
- Add `APIError.suspended` case
- Disable "Write today's message" button
- Show below it: "Your account has been suspended for violating community guidelines."
- Muted but visible
- Do not allow send screen to open
- Enforced both client-side AND server-side

## 5. Data & Privacy Constraints

- `sender_user_id` must never leave server
- No sender identity returned to clients
- No message plaintext logged
- No sender ID sent to Sentry
- No analytics introduced
- No public social graph
- Delivery log is audit-only, cleaned up after 48h
